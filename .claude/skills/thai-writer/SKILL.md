# Thai Writer: เขียนและแก้ภาษาไทยให้อ่านเหมือนคนไทยเขียนเอง

skill นี้ใช้เขียนหรือแก้ข้อความภาษาไทยให้อ่านเป็นธรรมชาติ ไม่มีกลิ่นแปลจากอังกฤษ และไม่มีร่องรอยที่ทำให้คนอ่านรู้ทันทีว่า AI เขียน โดยความหมายของต้นฉบับต้องอยู่ครบ ใช้ได้กับอีเมล แชท บทความ โพสต์โซเชียล เอกสารทางการ คู่มือ สรุปประชุม และสไลด์

งานบางอย่างไม่อยู่ในนี้ แคปชันขายของและการเช็กกฎหมายโฆษณาอยู่นอก scope ข้อความในซอฟต์แวร์ เช่น ปุ่ม error commit PR หรือ README ให้ใช้ [thai-product-writer](../thai-product-writer/SKILL.md) ซึ่งใช้ core ของ skill นี้อยู่แล้ว ส่วนปัญหาภาษาไทยในโค้ด เช่น slug ตัดคำ หรือวันที่ พ.ศ. ให้ใช้ [thai-i18n](../thai-i18n/SKILL.md)

## ลำดับการตัดสินใจ

```
Meaning > Context > Audience > Tone > Natural Thai > Punctuation & Formatting > AI-Smell Review > จำเป็นต้องแก้ไหม (NO_CHANGE)
```

ห้ามแก้คำก่อนรู้ context และ audience คำหรือเครื่องหมายเดียวกันอาจผิดที่หนึ่งแต่ถูกอีกที่หนึ่ง `ดังกล่าว` ในหนังสือราชการเป็นเรื่องปกติ แต่ในแชทกับเพื่อนร่วมงานจะฟังแข็ง (ดู [core/anti-ai.md](core/anti-ai.md))

## กฎที่ใช้เสมอ

1. em dash `—` และลูกศร `→` ในเนื้อความภาษาไทยห้ามเป็นค่าตั้งต้น ให้เขียนเป็นคำเชื่อมหรือเว้นวรรคแทน ดู [core/punctuation.md](core/punctuation.md)
2. รูปแบบต้องพอดีกับเนื้อหาและช่องทาง ข้อความสั้นไม่ต้องมีหัวข้อ ตัวหนา หรือ bullet และช่องที่ไม่ render Markdown ห้ามมีเครื่องหมาย Markdown ดู [core/formatting.md](core/formatting.md)
3. ไม่มี blacklist คำ คำไหนจะเป็นปัญหาต้องดูบริบท ความถี่ และระดับภาษา ข้อยกเว้นมีแค่สัญลักษณ์สองตัวในข้อ 1 ดู [core/anti-ai.md](core/anti-ai.md)

## ขั้นตอนการทำงาน

1. หา context และ audience ก่อนแตะคำไหน ข้อความนี้จะไปอยู่ที่ไหน ใครอ่าน แล้วเปิดไฟล์ใน `contexts/` ที่ตรงกับงาน
2. เช็กความหมายก่อนเรียบเรียงใหม่ ตัวเลข วันที่ ชื่อ เงื่อนไข และข้อผูกมัดต้องอยู่ครบ (ดู [core/meaning-preservation.md](core/meaning-preservation.md)) ถ้าต้นฉบับกำกวมจนเดาความหมายไม่ได้ ให้ถามผู้ใช้
3. เลือกโทนจากบริบทและผู้อ่าน ไม่ใช่จากความชอบ (ดู [core/tone.md](core/tone.md)) อีเมลถึงผู้บริหารกับข้อความ LINE ถึงเพื่อนในทีมใช้ระดับภาษาคนละแบบ
4. เรียบเรียงตาม natural-thai, clarity และ conciseness เขียนใหม่ทั้งประโยค ไม่ไล่แทนคำทีละคำ
5. ตรวจเครื่องหมายและรูปแบบ ค้นหา `—` และ `→` ดูว่า comma, colon และวงเล็บแต่ละตัวมีหน้าที่จริงไหม แล้วดูว่ารูปแบบพอดีกับช่องทาง (ดู [core/punctuation.md](core/punctuation.md) และ [core/formatting.md](core/formatting.md))
6. ตรวจ AI-smell ตามบริบท ไล่ตาม [review/thai-ai-smells.md](review/thai-ai-smells.md) แล้วถามว่า pattern นี้ผิดธรรมชาติในบริบทนี้จริงไหม สัญญาณเดียวยังไม่พอจะตัดสิน
7. ถามตัวเองว่าต้องแก้จริงไหม (NO_CHANGE) ถ้าข้อความเดิมผ่านทุกข้อข้างบนแล้ว ให้ตอบว่าไม่ต้องแก้ พร้อมเหตุผลสั้นๆ การแก้ทุกอย่างเพราะรู้สึกว่าต้องมีอะไรให้แก้ ก็ผิดพอๆ กับการไม่แก้อะไรเลย (ดู [benchmark/README.md](../../../benchmark/README.md))
8. ตรวจซ้ำด้วย [review/review-checklist.md](review/review-checklist.md) ก่อนส่ง

## เมื่อ AI เขียนเองตั้งแต่ต้น

กฎทั้งหมดในนี้ใช้กับข้อความที่ AI เขียนเองด้วย ไม่ได้มีไว้แก้งานของคนอื่นอย่างเดียว คำตอบในแชท อีเมลที่ร่างให้ผู้ใช้ สรุปประชุม หรือข้อความบนสไลด์ ต้องผ่านลำดับการตัดสินใจเดียวกัน และต้องผ่าน [review/review-checklist.md](review/review-checklist.md) ก่อนส่ง

นิสัยที่โมเดลมักติดมาตอนเขียนเองคือใส่หัวข้อกับตัวหนาให้คำตอบสามบรรทัด ใช้ em dash เชื่อมประโยค และปิดท้ายด้วยประโยคชวนถามต่อ ถ้าเจอในร่างของตัวเอง ให้แก้ก่อนส่ง ไม่ต้องรอให้ผู้ใช้ทัก

## วิธีส่งคำตอบ

1. ข้อความที่แก้แล้ว หรือบอกว่าไม่ต้องแก้พร้อมเหตุผลสั้นๆ
2. ถ้าแก้หลายจุด สรุปสั้นๆ ว่าแก้เพราะความหมายคลาดเคลื่อน เพราะไม่เข้ากับบริบท หรือเพราะ AI-smell ข้ามหมวดที่ไม่มีอะไรจะพูด
3. ถ้าผู้ใช้ขอแค่ให้แก้ ส่งเฉพาะข้อความที่แก้ ไม่ต้องแนบสรุป
