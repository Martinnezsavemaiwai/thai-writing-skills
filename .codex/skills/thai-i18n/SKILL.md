# Thai i18n: ภาษาไทยในโค้ดให้ถูกต้อง

skill นี้คนละเรื่องกับ [thai-product-writer](../thai-product-writer/SKILL.md) — นั่นคือการเขียนคำโฆษณา/คำบรรยายสินค้าให้อ่านเป็นธรรมชาติ ส่วนนี้คือการจัดการ**ข้อความภาษาไทยในซอฟต์แวร์**: slug, การตัดคำ, วันที่, การเรียงลำดับ ปัญหาที่นี่เป็นปัญหาทางเทคนิค ไม่ใช่ปัญหาเรื่องน้ำเสียง

## 1. แปลงชื่อไทยเป็น slug/URL (RTGS transliteration)

**ปัญหา:** อยากได้ URL ภาษาอังกฤษจากชื่อสินค้า/หัวข้อภาษาไทย (เช่น `/products/serum-bamrung-phiw` แทน `/products/เซรั่มบำรุงผิว`)

**สิ่งที่ต้องรู้ก่อนทำ:**
- มาตรฐานทางการคือ **RTGS (Royal Thai General System of Transcription)** — ไม่มีวรรณยุกต์ ไม่มีสระยาว/สั้นแยกชัดเจนเสมอไป และ**ถอดกลับเป็นภาษาไทยแบบเป๊ะไม่ได้** (คำไทยหลายคำสะกดต่างกันแต่ถอดเป็น RTGS แบบเดียวกัน) เพราะฉะนั้นอย่าคาดหวังว่าจะ round-trip กลับเป็นไทยได้จาก slug
- อย่าถอดตัวอักษรทีละตัวแบบ 1:1 เพราะสระไทยบางตัววางก่อน/บน/ล่าง/หลังพยัญชนะที่มันประกอบด้วย (เช่น สระเอ, สระไอ อยู่หน้าอักษร) ถอดตรงตัวจะได้ลำดับตัวอักษรผิด ให้ใช้ไลบรารีที่รองรับกฎ RTGS จริง (เช่น `pythainlp.transliterate` ฝั่ง Python) ไม่ใช่ regex แทนที่ทีละตัวอักษร
- **ทางเลือกที่ควรพิจารณาก่อน RTGS เสมอ:** ถ้า target ผู้ใช้เป็นคนไทย การเก็บ slug เป็นภาษาไทยตรงๆ (URL-encoded UTF-8, เบราว์เซอร์/ระบบยุคนี้รองรับหมดแล้ว) มักดีกว่าในแง่ SEO และผู้ใช้อ่านแล้วเข้าใจ ใช้ RTGS เมื่อ audience เป็นสากล/ต้องพิมพ์ URL เอง หรือระบบ backend ไม่รองรับ Unicode ใน path

**ตัวอย่างปัญหาที่พบบ่อย:** ถอด "เสื้อ" แบบ 1:1 ตามลำดับ unicode code point จะได้ลำดับตัวอักษรสลับ เพราะ "เ" เป็นสระที่เขียนไว้หน้าพยัญชนะ แต่ออกเสียงหลังพยัญชนะ — ต้องจัดลำดับใหม่ก่อนถอดเสียง

**แหล่งอ้างอิง:** [Royal Thai General System of Transcription (Wikipedia)](https://en.wikipedia.org/wiki/Royal_Thai_General_System_of_Transcription)

## 2. ตัดคำไทย: line-wrap และ search/tokenization

**ปัญหา:** ภาษาไทยไม่มีการเว้นวรรคระหว่างคำ (เว้นวรรคใช้คั่นประโยค/วลีเท่านั้น) ทำให้โค้ดที่ตั้งสมมติฐานว่า "คำ = string คั่นด้วย space" (แบบภาษาอังกฤษ) พังทันทีในสองจุดหลัก:

**Line-wrap ในหน้าเว็บ:** ข้อความไทยยาวๆ ไม่มี space ให้เบราว์เซอร์ตัดบรรทัด อาจล้นกล่อง (overflow) แทนที่จะขึ้นบรรทัดใหม่
- อย่าแก้แบบขี้เกียจด้วย `word-break: break-all` ทั้งหน้า เพราะมันจะตัดกลางคำอังกฤษ/ตัวเลขที่ปนอยู่ในข้อความไทยด้วย (เช่น ตัดกลาง "iPhone" หรือเลขรุ่นสินค้า)
- เบราว์เซอร์สมัยใหม่ส่วนหนึ่งรองรับการตัดคำไทยแบบ dictionary-based ในตัวอยู่แล้วตาม Unicode Line Breaking Algorithm (UAX #14) แต่ระดับการรองรับต่างกันตามเอนจิน ให้ทดสอบจริงบนเบราว์เซอร์เป้าหมายก่อนใส่ CSS แก้เอง อย่าสมมติว่าเหมือนกันหมด
- ถ้าต้องควบคุมจุดตัดเอง (เช่น PDF/canvas) ต้องตัดคำด้วย dictionary-based segmenter ก่อน (ดูหัวข้อถัดไป) แล้วแทรกจุดตัดบรรทัดเอง

**Search/tokenization:** การ index ค้นหาแบบ split ด้วย whitespace จะไม่แยกคำไทยเลย (ทั้งประโยคกลายเป็น token เดียว) ทำให้ค้นหาบางส่วนของคำไม่เจอ
- ใช้ dictionary-based word segmenter: ฝั่ง Python ใช้ **PyThaiNLP**, ฝั่ง JavaScript/เบราว์เซอร์ใช้ **`Intl.Segmenter('th', { granularity: 'word' })`** (รองรับใน engine สมัยใหม่ ตรวจ compatibility ก่อนใช้ใน production)
- Elasticsearch/OpenSearch มี Thai analyzer ในตัว (ใช้ ICU + dictionary) เปิดใช้แทนการเขียน tokenizer เอง
- PostgreSQL full-text search (`tsvector`) ไม่มี Thai dictionary ในตัว ต้อง segment คำก่อนแล้วค่อยส่งเข้า `to_tsvector('simple', ...)` หรือใช้ extension เพิ่ม

## 3. วันที่ พ.ศ./ค.ศ. และเลขไทย (CLDR)

**ปัญหา:** ปฏิทินราชการไทยใช้ **พ.ศ. (Buddhist Era) = ค.ศ. + 543** เอกสารราชการ/กฎหมายเกือบทั้งหมดต้องใช้ พ.ศ. ส่วนแอปผู้บริโภคทั่วไปใช้ ค.ศ. หรือทั้งคู่ก็ได้ ขึ้นกับกลุ่มเป้าหมาย — **ต้องถามให้ชัดว่างานนี้ต้องการปีแบบไหน อย่าเดา**

**วิธีทำให้ถูกต้อง:** ใช้ locale extension ของ CLDR แทนการบวกลบเลขเอง:
- `Intl.DateTimeFormat('th-TH-u-ca-buddhist', {...}).format(date)` ใน JavaScript จะคืนปี พ.ศ. ให้อัตโนมัติ
- **บั๊กที่พบบ่อย:** เอา `date.getFullYear()` (ซึ่งเป็น ค.ศ. เสมอ) ไป `+ 543` เองทั้งที่ format ด้วย `u-ca-buddhist` ไปแล้ว ทำให้ได้ปีเพี้ยนไปสองเท่า (บวกซ้ำ) ให้เลือกทางใดทางหนึ่ง ไม่ใช้ทั้งสองพร้อมกัน
- เลขไทย (๐-๙, locale extension `nu-thai`) มีอยู่จริงใน Unicode แต่ UI จริงแทบไม่มีใครใช้ (คนไทยอ่านเลขอารบิกกันปกติ) อย่าเปิด `nu-thai` เองโดยไม่มีคนขอ

**แหล่งอ้างอิง:** [Unicode CLDR — Buddhist Calendar](https://cldr.unicode.org/) (locale extension `u-ca-buddhist`)

## 4. การเรียงลำดับ (sort) ข้อความไทย

**ปัญหา:** เรียง string ไทยด้วย comparison ตัวอักษรตรงๆ (`<`, `Array.sort()` เปล่าๆ) จะได้ลำดับผิด เพราะสระบางตัวเขียนไว้**หน้า**พยัญชนะ (เ, แ, โ, ใ, ไ) แต่กฎการเรียงพจนานุกรมไทยต้องเรียงตาม**พยัญชนะ**ก่อน ไม่ใช่ตามตำแหน่ง code point

**วิธีแก้:** ใช้ collator ที่รองรับ locale แทนการเทียบ string ตรงๆ เช่น `Intl.Collator('th')` ใน JavaScript หรือ ICU collation ฝั่ง backend — ไม่ต้องเขียนกฎเรียงเอง

## เช็กก่อนใช้จริง

- ระบบเก่าบางระบบ (โดยเฉพาะที่เชื่อมกับหน่วยงานรัฐ/ธนาคารที่ยังไม่อัปเดต) อาจส่งไฟล์มาเป็น **TIS-620** แทน UTF-8 — เจอ mojibake (ตัวอักษรไทยกลายเป็นขยะ) ให้สงสัยเรื่อง encoding ก่อน ไม่ใช่คิดว่าข้อมูลเสีย
- ทุกข้อข้างบนควรตรวจกับ requirement จริงก่อนใช้ (ใช้ RTGS หรือ slug ไทยตรง, ต้องการ พ.ศ. หรือ ค.ศ., ต้องรองรับ Thai search จริงไหม) อย่าใส่ทุกอย่างเพราะ "ทำได้"
